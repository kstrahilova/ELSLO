## Architecture and Scope

ELSLO periodically computes weights for application replicas from latency and
failure metrics and writes them into a Traefik `IngressRoute`. Here a replica is
a Kubernetes **Service**, not an individual Pod. Traefik routes requests using
these weights; Linkerd supplies the outbound HTTP metrics collected by Linkerd
Viz Prometheus. The controller also checks backend reachability.

```text
client -> meshed Traefik -> meshed backend Services
               |                    |
               +-- Linkerd metrics -+-> Viz Prometheus
                                             |
                         ELSLO controller <--+
                                |
                                +-> update IngressRoute service weights
```

The submitted chart defaults to ELSLO only with `testingEnvironments: [gl]`.
The chart maps `gl` to the algorithm value `latency`
(ELSLO), `gels` to ELS, and `gl3`/`l3-rc` to L3. Keep the controller namespace
`custom-controller`: service accounts and authorization policies hard-code it.
Only run one controller for each managed route.

## 1. Prepare Tools and a Cluster

Required tools: Bash, curl, Docker (for the example image build and optional local
cluster), `kubectl`, Helm, and the Linkerd CLI. The local example also requires
k3d. Kubernetes administrator access is
needed to install CRDs, RBAC, Linkerd, and Traefik. Nodes need outbound image
registry access; the controller's builder also downloads Go modules.

The source deployment uses Go `1.25.7`; the reference tool versions are
Linkerd `edge-26.6.3` and Kubernetes client `1.34`. These are reference versions,
not a guarantee that every newer Kubernetes/Linkerd/Traefik combination works.
Use matching Linkerd CLI/control-plane versions and check compatibility with your
Kubernetes version before installing.

### Install Tools on Debian or Ubuntu

Skip tools already installed. These commands require `sudo` access and install
Docker from the distribution packages. On other operating systems, use the
official installation guides linked below.

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl tar gzip docker.io
sudo systemctl enable --now docker
sudo usermod -aG docker "$USER"
```

Log out and back in before continuing so the new group membership takes effect.
Docker group membership grants root-equivalent access to the host; use it only
for trusted users. Do not make the Docker socket world-writable.

Install the CLI binaries for the host's architecture. The versions are explicit
to make the setup repeatable; for an existing cluster, choose compatible versions
instead. The Helm version below is `3.19.0` and k3d is `5.8.3`.

```bash
case "$(uname -m)" in
  x86_64) arch=amd64 ;;
  aarch64|arm64) arch=arm64 ;;
  *) printf 'Unsupported host architecture\n' >&2; exit 1 ;;
esac
tools_dir=$(mktemp -d)

curl --fail --location "https://dl.k8s.io/release/v1.34.0/bin/linux/$arch/kubectl" \
  --output "$tools_dir/kubectl"
sudo install -m 0755 "$tools_dir/kubectl" /usr/local/bin/kubectl

curl --fail --location "https://get.helm.sh/helm-v3.19.0-linux-$arch.tar.gz" \
  --output "$tools_dir/helm.tar.gz"
tar -xzf "$tools_dir/helm.tar.gz" -C "$tools_dir"
sudo install -m 0755 "$tools_dir/linux-$arch/helm" /usr/local/bin/helm

curl --fail --location "https://github.com/k3d-io/k3d/releases/download/v5.8.3/k3d-linux-$arch" \
  --output "$tools_dir/k3d"
sudo install -m 0755 "$tools_dir/k3d" /usr/local/bin/k3d

curl --fail --location \
  "https://github.com/linkerd/linkerd2/releases/download/edge-26.6.3/linkerd2-cli-edge-26.6.3-linux-$arch" \
  --output "$tools_dir/linkerd"
sudo install -m 0755 "$tools_dir/linkerd" /usr/local/bin/linkerd

docker info
kubectl version --client
helm version
k3d version
linkerd version --client
```

Go and protobuf tools are installed inside the builder image in step 5; no host
Go installation is needed. Official tool documentation:

## 2. Install Linkerd and Linkerd Viz

On a new development cluster, use the Linkerd CLI's generated identity
certificates. For a persistent or multi-cluster installation, supply properly
managed identity certificates following the Linkerd documentation instead.

```bash
linkerd version --client
linkerd check --pre
linkerd install --crds | kubectl apply -f -
linkerd install | kubectl apply -f -
linkerd check
linkerd viz install | kubectl apply -f -
linkerd viz check
kubectl -n linkerd-viz get services prometheus metrics-api
kubectl -n linkerd-viz get servers.policy.linkerd.io
```

The chart expects Prometheus at
`http://prometheus.linkerd-viz.svc.cluster.local:9090/` and the metrics API at
`metrics-api.linkerd-viz.svc.cluster.local:8085`. It creates Linkerd authorization
policies targeting the Viz `Server` resources `prometheus-admin` and
`metrics-api`. If your Viz version uses different names or an external
Prometheus, adapt the configuration and access policies accordingly. Retain the
Linkerd sidecar on the controller so its service-account identity can authenticate.

## 3. Install and Mesh Traefik

Use Traefik v3 with its Kubernetes CRD provider enabled. Its Deployment must be
named **`traefik`**, because the controller's Prometheus queries contain
`deployment=~"traefik"`. Inject its Pods into Linkerd before generating traffic.

```bash
helm repo add traefik https://traefik.github.io/charts
helm repo update
kubectl create namespace traefik
kubectl annotate namespace traefik linkerd.io/inject=enabled --overwrite
helm upgrade --install traefik traefik/traefik --namespace traefik \
  --set fullnameOverride=traefik \
  --set providers.kubernetesCRD.enabled=true \
  --set providers.kubernetesCRD.allowCrossNamespace=true
kubectl -n traefik rollout status deployment/traefik --timeout=5m
kubectl get crd ingressroutes.traefik.io
linkerd -n traefik check --proxy
```

Cross-namespace routing is needed when backend Services reside outside the route
namespace. Enable it only in a cluster where this routing model is acceptable.
On an existing Traefik installation, adapt that installation instead of creating
a competing ingress controller. Restart existing Pods after enabling injection.

## 4. Deploy Hotel Reservation and Its Managed Route

The submission includes the [benchmark-apps chart](benchmark-apps/Chart.yaml)
and uses the Hotel Reservation chart from
[DeathStarBenchFork](https://github.com/kstrahilova/DeathStarBenchFork) as a
local Helm dependency. The dependency path expects both repositories to be
siblings under the same project directory. From the root directory of this repo,
clone the app repository there if it is not already available:

```bash
if [ ! -d ../../DeathStarBenchFork/.git ]; then
  git clone https://github.com/kstrahilova/DeathStarBenchFork.git ../../DeathStarBenchFork
fi
```

The dependency is a local `file://` chart path, so `helm dependency build`
requires this checkout at that location. The chart and application defaults are
based on the upstream [Hotel Reservation documentation](https://github.com/kstrahilova/DeathStarBenchFork/blob/master/hotelReservation/README.md).
The benchmark chart declares two instances of the Hotel Reservation chart, each
with a distinct frontend Service.
It enables Linkerd injection and exposes the app's `/health` endpoint on port
8081, which the controller requires. The accompanying Traefik `IngressRoute`
is named `hotel-reservation-frontend-gl-route`, has one route and a nonempty
label map, and starts with equal weights for both Services.

The benchmark chart installs two complete Hotel Reservation stacks, not just
two frontend Pods. This preserves the independent Service backends used by the
weighting algorithm, but requires substantially more cluster resources than the
minimal two-Service sample. The generated route contains exactly one route, two
uniquely named Services, explicit namespaces/ports/weights, `nativeLB: true`,
and a nonempty label map. The DSB chart and the submitted benchmark chart values
can be adjusted in [benchmark-apps/values.yaml](benchmark-apps/values.yaml).

**An HTTPS domain is required to run the benchmark CronJob.** Configure a DNS
name that resolves to Traefik and is reachable from the cluster, enable HTTPS
on Traefik, and provide a TLS certificate for that name. The CronJob URL is 
`https://hotel-reservation.<hostName>.<domainName>:443`. The route template
derives its `Host(...)` rule from those same `hotelReservation.name`, `hostName`,
and `domainName` values, uses Traefik's `web` entry point, and references
the Secret configured by `tls.secretName`. Set `hostName` and `domainName` to
the DNS name components for a domain that resolves to Traefik from both outside
and inside the cluster. The TLS Secret must contain a certificate valid for the
resulting full hostname and exist in the `hotel-reservation-gl` namespace.

Set the domain and TLS Secret name in [benchmark-apps/values.yaml](benchmark-apps/values.yaml),
or provide equivalent Helm overrides. Create the namespace and certificate
Secret before installing the chart:

```bash
kubectl create namespace hotel-reservation-gl --dry-run=client -o yaml | kubectl apply -f -
kubectl -n hotel-reservation-gl create secret tls hotel-reservation-tls \
  --cert=/path/to/tls.crt --key=/path/to/tls.key
```

Replace the certificate paths and Secret name with your own. The chart values'
`tls.secretName` must match the Secret created in the route namespace.

Install the chart and verify the app and route:

```bash
helm dependency build ./benchmark-apps
helm lint ./benchmark-apps
helm upgrade --install hotel-reservation ./benchmark-apps \
  --namespace hotel-reservation-gl
kubectl -n hotel-reservation-gl rollout status deployment/frontend-hotel-reservation-a --timeout=10m
kubectl -n hotel-reservation-gl rollout status deployment/frontend-hotel-reservation-b --timeout=10m
kubectl -n hotel-reservation-gl get services,endpointslices
kubectl -n hotel-reservation-gl get ingressroute hotel-reservation-frontend-gl-route
```

Once configured, the benchmark chart's `wrk2` CronJob sends workload to the
same HTTPS domain every five minutes and runs for the configured duration (300
seconds by default). The benchmark container expects `wrk2` at
`/usr/local/bin/wrk`. Its thread, connection, duration, and request-rate settings
are under `hotelReservation.hrClient` in
[benchmark-apps/values.yaml](benchmark-apps/values.yaml).

```bash
kubectl -n hotel-reservation-gl get cronjob hotel-reservation-benchmark
kubectl -n hotel-reservation-gl get jobs
kubectl -n hotel-reservation-gl logs -f job/<job-name>
```

Wait for the next five-minute schedule to create a Job, then use its name in the
logs command. Keep the CronJob enabled while verifying metrics and controller
updates. The request profile is
[mixed-workload_type_1.lua](benchmark-apps/benchmark-load-gen/hotel-reservation/mixed-workload_type_1.lua).
This generates traffic to exercise the app and metrics path; it is not a
benchmark result or a substitute for application data preparation.

## 5. Build and Load Your Builder Image

The chart mounts the submitted Go sources through ConfigMaps, generates the
metrics API protobuf bindings, and compiles the controller in an init container.
It does not expect a precompiled controller image. You must build your own
builder image using the command below. The chart already references
`elslo-builder:local`, matching the build command, so no image-reference changes
in the deployment or values are needed. No prebuilt builder image or original
registry credentials are required. From the root folder of this repo,
build using the included [Dockerfile.protoc](Dockerfile.protoc):

```bash
docker build -f Dockerfile.protoc -t elslo-builder:local .
```

The Dockerfile downloads a Linux x86-64 protoc binary, so the supplied recipe
requires a Linux AMD64 build environment and AMD64 target nodes. For ARM64,
adapt the protoc download to that architecture before building.

The host Docker image store is separate from the Kubernetes nodes' image stores.
For the local k3d cluster, import the image before deploying the controller:

```bash
k3d image import elslo-builder:local --cluster elslo
```

For another cluster, export the image and load it into the container runtime on
**every node that may run the controller**, preserving the same name and tag:

```bash
docker image save elslo-builder:local --output elslo-builder.tar
```

Transfer the archive to each node using their image-import mechanism.
Build for the target nodes' CPU architecture. Merely building on
your workstation is not enough.

If your cluster does not allow node image imports, publish the builder to your
own accessible registry and override `baseImage.name` and `baseImage.tag` in a
Helm values file. This alternative still requires no edits to the deployment
template. Public registries do not require a pull secret. For a private registry,
choose one of the following options. In both cases the Secret must exist in the
`custom-controller` namespace and its name must match `imagePullSecret`.

### Private Registry: Create the Secret Directly

Set these top-level entries in [values.yaml](custom-controller/values.yaml):

```yaml
imagePullSecret: controller-pull-secret
sealedSecrets: false
```

Create a standard Kubernetes Secret before deploying the controller; no Sealed
Secrets installation is needed. Replace `registry.example.com` with the registry
hosting your builder image. Docker prompts for your registry credentials; use a
read-only pull credential where possible. An isolated Docker configuration keeps
this operation separate from your existing login configuration:

```bash
registry_config=$(mktemp -d)
docker --config "$registry_config" login registry.example.com
kubectl create namespace custom-controller --dry-run=client -o yaml | kubectl apply -f -
kubectl -n custom-controller create secret generic controller-pull-secret \
  --type=kubernetes.io/dockerconfigjson \
  --from-file=.dockerconfigjson="$registry_config/config.json" \
  --dry-run=client -o yaml | kubectl apply -f -
rm "$registry_config/config.json"
rmdir "$registry_config"
```

The chart only references this manually managed Secret; it does not create or
replace it. Do not commit credentials or the temporary Docker configuration.

### Private Registry: Use Sealed Secrets

Set these top-level entries instead:

```yaml
imagePullSecret: controller-pull-secret
sealedSecrets: true
```

Install the Sealed Secrets controller and replace the bundled template's
encrypted credentials with your own, sealed for the target cluster. Render in
the `custom-controller` namespace as shown in step 6. The original encrypted
credentials cannot be reused on a fresh cluster. Verify that the Sealed Secrets
controller creates the underlying pull Secret before expecting the builder to
start. Setting `sealedSecrets: true` alone does not create a SealedSecret when
`imagePullSecret` is empty.

## 6. Configure and Deploy ELSLO

The included [values.yaml](custom-controller/values.yaml) already selects ELSLO
(`testingEnvironments: [gl]`), the `hotel-reservation-frontend` application prefix,
and a latency SLO of 200 ms. Use these defaults for this setup; no additional
values file is needed. For another application, adjust `env.APPLICATION_TO_MANAGE`
and `env.SLOS` in that file before rendering the chart.

The latency threshold is in milliseconds. Use a threshold present in Linkerd's
`response_latency_ms_bucket` histogram (the default is `200`); the implementation
looks up that exact bucket rather than interpolating a threshold.

The default `imagePullSecret: ""` disables both the pull-secret reference and
SealedSecret creation. `sealedSecrets` is unset by default and is treated as
false. Render the complete chart directly; no template exclusions or Sealed
Secrets installation are needed for the locally built image or a directly
created pull Secret.

```bash
kubectl create namespace custom-controller --dry-run=client -o yaml | kubectl apply -f -
helm lint ./custom-controller
helm template elslo ./custom-controller --namespace custom-controller > elslo-rendered.yaml
kubectl apply --dry-run=server -n custom-controller -f elslo-rendered.yaml
kubectl apply -n custom-controller -f elslo-rendered.yaml
kubectl -n custom-controller get pvc gocache-pvc
kubectl -n custom-controller logs deployment/custom-controller-gl -c builder -f
```

The chart includes a fixed-name, 512 MiB `hostPath` PV at `/data/go-cache`, with
an explicitly bound PVC. This is appropriate for the single-node example, not
portable shared storage. On a multi-node/managed cluster, adapt storage to your
storage class and scheduling policy before applying; `hostPath` may be forbidden
by cluster policy. The cache is disposable, but the chart's reclaim policy is
`Retain`. Fixed resource names also mean this chart is not suitable for multiple
independent installations in one cluster without modification.

Compilation can take several minutes and requires access to Go module sources.
After the builder finishes:

```bash
kubectl -n custom-controller rollout status deployment/custom-controller-gl --timeout=15m
kubectl -n custom-controller logs deployment/custom-controller-gl -c controller --tail=100
linkerd -n custom-controller check --proxy
```

Selecting `testingEnvironments: [gl]` is what restricts this deployment to ELSLO.

## 7. Verify Operation

```bash
kubectl auth can-i update ingressroutes.traefik.io \
  --as=system:serviceaccount:custom-controller:custom-controller-sa \
  --namespace hotel-reservation-gl
kubectl -n hotel-reservation-gl get ingressroute hotel-reservation-frontend-gl-route -o yaml
kubectl -n custom-controller logs deployment/custom-controller-gl -c controller -f
```

Expect the controller log to name the managed route, report estimated latency
and weights, and reconcile the route. The route's `weightsComputedAt` label and
service weights should update while traffic is flowing. Normal reconciliation
is every 10 seconds, with a longer retry interval on some no-data/error paths.
Readiness only checks process health; it does not prove that metrics exist or
that weights are being updated.

To inspect raw metrics from a second terminal:

```bash
kubectl -n linkerd-viz port-forward service/prometheus 9090:9090
```

Open `http://localhost:9090` and query:

```promql
sum by (dst_service, le) (
  irate(response_latency_ms_bucket{deployment="traefik",direction="outbound"}[10m])
)
```

Confirm that the expected backend names and the SLO bucket are present. Allow
at least two Prometheus scrapes after starting traffic. Keep traffic running
long enough to obtain useful histograms. Do not run another reconciler that
continually restores the route weights that ELSLO changes.
The backend service names in this chart are `frontend-hotel-reservation-a` and
`frontend-hotel-reservation-b`.

## Configuration Reference

Settings are in [values.yaml](custom-controller/values.yaml); edit entries under
`env` unless stated otherwise.

| Setting | Default | Meaning |
| --- | --- | --- |
| `testingEnvironments` | `[gl]` | ELSLO only; other variants are disabled by default. |
| `imagePullSecret` (top-level) | `""` | Name of the pull Secret in `custom-controller`; empty disables the reference and SealedSecret creation. |
| `sealedSecrets` (top-level) | Unset (false) | Set to `true` with a nonempty `imagePullSecret` to render the bundled SealedSecret; leave false for a directly created Secret. |
| `APPLICATION_TO_MANAGE` | `hotel-reservation-frontend` | Route prefix; watched name is `<prefix>-gl-route`. |
| `PROMETHEUS_ADDRESS` | `http://prometheus.linkerd-viz.svc.cluster.local:9090/` | Prometheus HTTP API. |
| `METRICS_API_ADDRESS` | `metrics-api.linkerd-viz.svc.cluster.local:8085` | Linkerd Viz gRPC API, also used by other estimator variants. |
| `SLOS` | `{"latency": 200}` | JSON map of latency threshold in milliseconds. |
| `PROMETHEUS_TIME_WINDOW` | `10m` | Prometheus query range. |
| `METRICS_TIME_WINDOW` | `20s` | Metrics API time window. |
| `FAILURE_PENALTY` | `2000` | Fallback failure penalty for ELSLO. |
| `EXPONENTIAL_DECAY_PARAM` | `0.2` | Exponential forward-decay parameter. |
| `POLYNOMIAL_DECAY_PARAM` | `2` | Polynomial forward-decay parameter. |
| `FD_REFRESH_PERIOD` | `2` | Forward-decay landmark refresh interval in minutes. |
| `AGGREGATION_TIME_WINDOW` | `5s` | Aggregation time window. |
| `EWMA_DECAY_PARAM` | `5s` | EWMA parameter for variants configured to use EWMA. |

The deployment template supplies `LATENCY_ESTIMATION_ALGORITHM=latency`,
`AGGREGATION_ALGORITHM=decay`, and `AGGREGATION_FUNCTION=exp` for `gl`; do not
duplicate these entries in `env`. All numeric parameters parsed at startup must
remain valid, including parameters unused by the selected estimator.

## Updating and Stopping

After changing benchmark-app values, or after updating the local app chart source,
rebuild dependencies and reapply the chart:

```bash
helm dependency build ./benchmark-apps
helm upgrade --install hotel-reservation ./benchmark-apps \
  --namespace hotel-reservation-gl
```

After changing controller source or values, rerun the render and apply commands
in step 6. The controller chart includes source checksums to trigger rebuilding
on source changes. For an explicit rebuild/restart:

```bash
kubectl -n custom-controller rollout restart deployment/custom-controller-gl
kubectl -n custom-controller rollout status deployment/custom-controller-gl --timeout=15m
```

To pause weight updates without removing the route or application:

```bash
kubectl -n custom-controller scale deployment/custom-controller-gl --replicas=0
```

To remove the benchmark application and route, uninstall the Helm release:

```bash
helm uninstall hotel-reservation --namespace hotel-reservation-gl
```

Uninstalling the release removes its CronJob, so it will no longer schedule new
load-generation Jobs. To pause generation without removing the benchmark:

```bash
kubectl -n hotel-reservation-gl patch cronjob hotel-reservation-benchmark \
  --type merge -p '{"spec":{"suspend":true}}'
```

The namespace remains after uninstall. Delete it only if it contains no other
resources you need; namespace deletion removes everything in it. The controller
and cluster infrastructure remain installed.

To remove only the resources rendered in this guide:

```bash
kubectl delete -n custom-controller -f elslo-rendered.yaml
```

This also deletes the rendered PV/PVC objects, but retained host cache files may
remain. It does not uninstall Traefik, Linkerd, or the application. Delete the
disposable local cluster only when finished with all its workloads:

```bash
k3d cluster delete elslo
```

## Troubleshooting

| Symptom | Checks |
| --- | --- |
| `ImagePullBackOff` | Build `elslo-builder:local` and import it into k3d or every eligible node's runtime; check CPU architecture. For the registry alternative, check your registry access and image-pull Secret. |
| Pod remains `Pending` | `kubectl -n custom-controller describe pod <pod>`; check PVC binding, storage policy, and available resources. |
| Builder fails | Read `-c builder` logs; check Go module access, `protoc`, both Go protobuf plugins, and node architecture. |
| `Forbidden` or metrics connection errors | Check Linkerd injection, Viz Server names/authorization policies, DNS, NetworkPolicies, and the configured API addresses. |
| Healthy controller but no route updates | Check exact route name, nonempty labels, a single route, explicit service namespaces/weights, backend endpoints, and HTTP 200 from each Service's `:8081/health`. |
| No metrics, skipped reconciliation, or restarts | Generate HTTP traffic through the meshed `traefik` Deployment; inspect the Prometheus query above and controller logs, including `--previous` after a crash. Some empty-metric paths terminate the process. |
| Incorrect/missing backend statistics | Ensure distinct Service names and the exact SLO histogram bucket; confirm HTTP is not classified as opaque TCP. |
| Weights keep reverting | Stop any other reconciler or automation that restores the route's original weights. |

## Multi-Cluster Deployments

Steps 1-7 describe a single-cluster run. Multi-cluster deployment
is optional and requires additional networking and identity configuration.

For multi-cluster experiments, provision and validate each cluster separately,
install Linkerd multicluster using a shared identity trust anchor, provide
network connectivity between gateways and Kubernetes API endpoints, and export
and mirror the chosen backend Services using the Linkerd version's multicluster
guide. List the local/mirrored Services explicitly in the managed route. Verify
reachability and per-Service metrics before enabling ELSLO. The included
benchmark chart is configured for a single cluster; the original distributed
benchmark topology and experiment orchestration are not reproduced here.

- `templates/`, `values.yaml`: deployment, source ConfigMaps, RBAC, and storage.

This guide describes deployment from the submitted sources. It requires the
DeathStarBenchFork source checkout for the local Helm dependency and a working
cluster metrics pipeline. Rendering either chart alone does not validate those
components.
